### 2026-08-01 — MM-42: SLA timer (`MARGIN_CALL_SLA_MINUTES`) with met/breached outcomes

### 2026-08-01 — MM-38: Persisted (Azure SQL) LangGraph checkpointing + idempotent run handling + per-run correlation id
- **Done:** `src/persistence/db/checkpoint_saver.py` — `AzureSQLSaver(BaseCheckpointSaver)`, a from-scratch implementation of LangGraph's checkpointer contract (`get_tuple`/`list`/`put`/`put_writes`/`delete_thread`) against this project's own SQL database via the existing `session_factory`. No official LangGraph checkpoint backend exists for SQL Server (only Postgres/SQLite/MongoDB/Redis), confirmed by checking installed packages before building this — see the user-confirmed decision in this story's planning. Stores each checkpoint's full `channel_values` inline per row (two new tables, `orchestrator_checkpoints`/`orchestrator_checkpoint_writes`, migration `10c2cb8a9b6d`) rather than replicating the official Postgres/SQLite savers' per-channel blob-dedup scheme — this orchestrator's graph is small/linear and doesn't need cross-checkpoint blob sharing. `build_orchestrator_graph()`'s default checkpointer is now `AzureSQLSaver` (was `InMemorySaver`). `MarginCallState.correlation_id` is now auto-generated (`uuid4().hex` via a Pydantic `default_factory`) instead of required from the caller. Added structured (structlog) logging bound to `correlation_id`/`thread_id`/`counterparty_id` at every node and at `start_run`/`resume_run`/`get_or_start_run` (satisfies CLAUDE.md's "every agent action is logged with a correlation id" rule) — deliberately does *not* write to `AuditLogORM`, which `persistence/db/models.py` explicitly reserves for MM-91/Phase 9. New `get_or_start_run(graph, state)`: checks `graph.get_state(config)` before dispatching: if a run already exists for `thread_id_for(event_id, counterparty_id)` (paused or finished), returns its current state instead of re-invoking the graph — the idempotency guarantee CLAUDE.md requires ("replaying the same event must not double-raise a call").
- **Real bug found and fixed (the significant one this story):** an intermittent (~1-in-5 to 1-in-8 runs) failure where `resume_run()`'s result was missing `approval_decision` entirely, or the resumed graph interrupted *again* instead of completing. Root-caused via a 300-iteration repro script plus direct inspection of the stored checkpoint/write rows: LangGraph's Pregel runtime executes via an internal `ThreadPoolExecutor` and calls checkpointer methods (`put`/`put_writes`) *concurrently*, even for this project's simple sequential graph — confirmed by finding `ThreadPoolExecutor` usage directly in `langgraph/pregel/_runner.py`/`_loop.py`/`_executor.py`. `AzureSQLSaver` wasn't thread-safe: two concurrent `put()` calls against the same SQLite connection (test fixture) could race and silently drop a checkpoint row — one specific reproduced case showed a checkpoint whose `put_writes()` call succeeded (the `__interrupt__` sentinel write was on disk) but whose corresponding `put()` call never landed, so `get_state()` couldn't find the pending interrupt to resume against and the graph paused fresh instead of resuming. Fixed with a single `threading.Lock` guarding every DB-touching method. `list()` needed care: it's a generator, and a lock held via `with self._lock:` wrapping a bare `yield` would stay acquired for the generator's *entire lifetime* (only released once fully consumed/closed/GC'd) — rewritten to materialize results eagerly inside the lock, then `yield from` the plain list afterward. Re-ran the 300-iteration repro after the fix: 0 failures (was previously reproducing within the first ~10 iterations most runs). Added a permanent regression test (`test_concurrent_puts_do_not_lose_checkpoints`, `ThreadPoolExecutor` with 8 workers writing 20 checkpoints) to `tests/unit/test_checkpoint_saver.py` so this can't silently regress.
- **Real end-to-end verification:** smoke-tested the saver directly against the real local `azure-sql-edge` container (not just SQLite-mocked unit tests) before writing any tests — a pause/resume cycle, then a *second* `AzureSQLSaver`/graph instance pointed at the same DB (simulating a process restart) correctly resumed. `tests/integration/test_checkpoint_saver_live.py` codifies this (auto-skips cleanly if the DB is unreachable, matching `test_db_schema.py`'s existing convention — this is a local-DB test, not a paid-third-party-API `@pytest.mark.live` test). Full suite re-run 5x consecutively after the fix with zero flakes (previously flaked roughly 1 in 5-8 full-suite runs before the lock was added).
