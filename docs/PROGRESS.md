### 2026-08-27 — MM-102 (follow-up #2): price-poller reverted -- it defeated Azure SQL Serverless auto-pause
- **Done:** The user asked a pointed question right after the poller shipped: does anything hit Azure SQL automatically, even when nobody's using the app -- given a prior real bill scare on this same Azure account. Checked the actual database config (`az sql db show`): `finsight-sql-server`/`FinSight_AI` is **Serverless** (`GP_S_Gen5_2`, `autoPauseDelay: 60` minutes, `minCapacity: 0.5` vCores) -- bills per-second while "Online," pauses to near-zero cost after an hour idle. The `price-poller` container added in the previous entry touched the DB every 60 **seconds**, far more often than the 60-**minute** pause threshold -- it would have kept the database permanently Online and billing continuously, 24/7, regardless of real usage. - **Bonus finding:** this also retroactively explains every "Login timeout expired" (HYT00) flakiness hit throughout MM-102/103's deployment work, previously attributed to vague "Azure Gateway throttling." It was Serverless auto-pause the whole time -- the first connection after 60+ idle minutes has to wait for Azure to resume the database (up to ~30s), and pyodbc's default login timeout is shorter than that, so a cold-start connection fails with an error indistinguishable from a real outage.
- **Decisions:** Stopped and removed the running `price-poller` container immediately (before anything else), reverted the live `docker-compose.yml` on the instance, then fixed the code properly: removed the `price-poller` service from `infra/compute.tf`'s embedded compose (another in-place `terraform apply`, 0 destroy); kept `streaming/latest_price_poller.py` itself (tested, functional) but re-documented it as an on-demand tool -- a short, bounded run right before a demo -- not an always-on service. Separately fixed the actual cold-start problem properly: `connect_args={"timeout": 60}` on both `get_engine()` and `migrations/env.py`'s separate engine (pyodbc/Microsoft's own documented fix for Serverless auto-resume -- raise the login timeout, no retry loop needed). `pool_pre_ping` (already present) and this new timeout address two different failure modes: a stale *pooled* connection vs. a fresh cold-start one.
- **Changed:** `infra/compute.tf` (removed `price-poller` service), `src/persistence/db/engine.py` (`AZURE_SERVERLESS_RESUME_TIMEOUT_SECONDS`, `connect_args`), `migrations/env.py` (same `connect_args`), `src/streaming/latest_price_poller.py` (docstring), `Makefile` (comment).

### 2026-08-19 — MM-75: Resilience -- retries, timeouts, dead-letter path for failed events (Phase 9 complete)
- **Done:** Picked up ROADMAP.md's MM-93 line, the last remaining Phase 9 story. Investigated before coding and found the real gap: `streaming/event_agent.py`'s `run()` -- the only real Kafka consumer loop in the codebase (the `market.impact` topic the Event Agent publishes to has no consumer today; `POST /simulate` triggers the orchestrator directly in-process, bypassing Kafka entirely, same as `/approve`/`/respond`) -- had zero error handling. Any exception from `handle_message` (a bad payload, a DB hiccup, a producer delivery failure) propagated uncaught, crashing the whole process *before* the offset was committed. On restart the exact same poison message would be redelivered and crash it again -- a permanent crash-loop wedging the partition for every message behind it, since Kafka offsets are strictly sequential per partition. Confirmed scope with the user before coding: harden the Event Agent's consumer specifically, not also add retry to the orchestrator's Slack/ServiceNow calls (a broader option offered and declined).
  New `_handle_with_retry()` (`event_agent.py`) wraps `handle_message` with a bounded, uniform retry budget (`EVENT_AGENT_MAX_ATTEMPTS = 3`, exponential backoff `1s, 2s`) -- a fresh DB session per attempt via `session_factory()`, since a session that raised mid-transaction can't just be reused for the next attempt. Every exception is retried the same way rather than trying to classify "transient" vs "will never succeed" -- a deterministic failure (e.g. malformed JSON) just costs a few seconds of backoff before landing in the dead-letter queue, simpler than building a classifier and just as safe. Once the budget is exhausted, `_publish_dead_letter()` publishes a new `DeadLetterEvent` (original `topic`/`partition`/`offset`/`key`/raw `value`, `error_type`/`error_message`, `attempts`, `failed_at`) to a new `market.dead-letter` topic (`Settings.kafka_topic_dead_letter`) and `run()` still commits the original offset -- the poison message can no longer wedge the consumer. `_publish_dead_letter` deliberately does *not* catch its own failure: if Redpanda itself is unreachable, letting `ProducerDeliveryError` propagate and crash `run()` (offset still uncommitted, safe to retry after restart) is the right outcome -- a materially bigger, more visible problem than one bad message, not something to paper over.
  **Timeouts were audited, not speculatively added:** every external I/O call in this path already has an explicit timeout -- `EventConsumer.poll()` (1s), `EventProducer.flush()` (10s), and MM-69's CoinGecko `_get_with_retry` backoff for the market-data path. The new retry budget itself is what bounds total time spent on any one message, so no new timeout mechanism was needed on top of what already existed -- flagged this explicitly rather than inventing something to check a box.
- **Decisions:** Confirmed scope with the user via `AskUserQuestion` before coding -- Event Agent consumer only (recommended) vs. also adding retry to Slack/ServiceNow calls; user chose the narrower, literal scope. Chose uniform retry-then-DLQ over classifying exception types as transient/permanent -- simpler, and the cost of retrying a doomed message is bounded and small.

### 2026-08-01 — MM-42: SLA timer (`MARGIN_CALL_SLA_MINUTES`) with met/breached outcomes
- **Done:** `await_sla_response(state, settings)` -- pauses (LangGraph `interrupt()`) after `send_notification`, resolving `"met"` if a response signal arrives before the deadline, or `"breached"` once the deadline has passed. Modeled as an external poll/resume loop, not an in-process sleep: `MARGIN_CALL_SLA_MINUTES` defaults to 60, and a graph node blocking a worker for an hour isn't viable (same reason `await_approval` uses `interrupt()` rather than blocking). The node calls `interrupt()` in a `while True:` loop -- if resumed with neither a `"responded"` signal nor a passed deadline, it loops back and calls `interrupt()` again, re-pausing (proven correct via a standalone repro before relying on it: each external `resume_run()` call only ever resolves the *next* still-open `interrupt()` call in that node's execution, so looping-and-re-pausing genuinely works across separate external invocations). `send_notification` now also records `notification_sent_at`. New `MarginCallState.sla_outcome`/`notification_sent_at` fields. Graph wiring: `send_notification -> await_sla_response -> END` (unconditional -- `_route_after_approval` already keeps a `"rejected"` decision from ever reaching `send_notification`, so nothing new needed there). New provisional endpoints `POST /margin-calls/{thread_id}/respond` (simulates the counterparty responding -- no real counterparty channel exists in this demo) and `POST /margin-calls/{thread_id}/check-sla` (re-evaluates the deadline; a no-op if called too early -- there's no real scheduler yet), both following MM-37's "ships now, provisional, revisit later" pattern, documented with a matching note in `ROADMAP.md`.
- **Real bug found and fixed during design, before writing any orchestrator code:** a first attempt at the pause/resume-loop pattern resumed with an *empty* dict (`Command(resume={})`) for the "just check the deadline" case, and the node would then re-pause on *every single resume* regardless of how much time had passed -- confirmed via a minimal standalone repro (printing from inside the node showed the code after `interrupt()` was never reached at all on the empty-dict resume, despite the node function visibly executing).
